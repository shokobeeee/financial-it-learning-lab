📁 Directoryの r / w / x はFileと意味が違う

r = list
ディレクトリ内の名前一覧を読む。
w = create/delete
中にファイルを作る・削除する。
x = traverse
そのディレクトリを通過して中へ到達する。
実験
$ ls -ld /srv/project drwxr-x--- root developers /srv/project
面白いポイント
r だけ: 名前一覧は読めても、中のfileへ到達できないことがある x だけ: 名前を知っていれば到達できても、lsで一覧は出せない r + x: 一覧も参照もできる

👥 owner / group / chown / chgrp

report.txtの所有者
$ ls -l /srv/project/report.txt -rw-r----- 1 root developers 1200 Aug 17 report.txt
Groupメンバーシップ
$ id learner uid=1000(learner) gid=1000(learner) groups=1000(learner),1100(developers)

Group追加後は、新しいLogin sessionでSupplementary Groupが反映される点も現場では重要です。

🧮 umask — 新しく作るFileの初期Permission

umask 022 file: 666 - 022 → 644 dir: 777 - 022 → 755
考え方
新規Fileの最大ベース: 666 = rw-rw-rw- 新規Directoryの最大ベース: 777 = rwxrwxrwx umaskは「付けない権限」を指定する 例: umask 077 file → 600 dir → 700

🛡 sudo — rootになるのではなく「許可された管理操作を借りる」

sudoersを試す
User許可
learnerALL=(ALL:ALL) ALL
aliceなし
なぜvisudo？
$ sudo -l User learner may run the following commands: (ALL : ALL) ALL # sudoersを壊すと管理操作できなくなるので # 構文チェック付きのvisudoを使う

📋 ACL — owner/group/othersだけでは足りない例外許可

aliceだけreport.txtを読めるようにする
user::rw-
group::r--
other::---
確認
$ getfacl /srv/project/report.txt # owner: root # group: developers user::rw- group::r-- other::---

ls -lに + が付いていたらACLが設定されている可能性があります。

✨ 特殊Permission — 知っておくと現場で困りにくい

setuid
実行時にfile ownerの権限を使う。代表例としてpasswdなどで見かける。
setgid
Directoryで使うと、新規fileがDirectoryのgroupを継承しやすい。
sticky bit
共有Directoryで、自分のfile以外を勝手に削除しにくくする。/tmpなど。
$ ls -ld /tmp drwxrwxrwt ... /tmp # 最後の t = sticky bit

Permission deniedの一次切り分け順
1. whoami / id 誰として実行？ 2. ls -l owner / group / rwx 3. namei -l path 親Directoryのxも確認 4. groups / id 必要Groupに所属？ 5. getfacl ACLの追加制御は？ 6. sudo -l 管理権限が必要な操作？
